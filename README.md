# Базовая шпаргалка для CMake

<details>
<summary><b>Для тех кто уже знает и хочет посмотреть команды:</b></summary>

<br>

<details>
<summary><b>add_subdirectory</b></summary>

<br>

```cmake
add_subdirectory(src)
```

Подключает другую директорию к сборке. CMake заходит в эту папку и ищет там
свой `CMakeLists.txt`.

Например, если в главном файле написать `add_subdirectory(src)`, то CMake перейдет
в папку `src` и выполнит команды из `src/CMakeLists.txt`.

</details>

<details>
<summary><b>add_library</b></summary>

<br>

```cmake
add_library(core)
```

Создает target-библиотеку. В нашем случае target называется `core`.

Сама команда только создает метку библиотеки. Файлы к ней можно добавить потом через
`target_sources`.

</details>

<details>
<summary><b>target_sources</b></summary>

<br>

```cmake
target_sources(core
    PRIVATE
        math_utils.cpp
)
```

Добавляет исходные файлы к target.

Здесь мы говорим: target `core` собирается с файлом `math_utils.cpp`.

`PRIVATE` означает, что этот `.cpp` файл нужен только самой библиотеке `core`.

</details>

<details>
<summary><b>add_executable</b></summary>

<br>

```cmake
add_executable(app main.cpp)
```

Создает target исполняемого файла.

В примере будет создан исполняемый файл `app`, который собирается из `main.cpp`.

</details>

<details>
<summary><b>target_include_directories</b></summary>

<br>

```cmake
target_include_directories(core
    PUBLIC
        ${PROJECT_SOURCE_DIR}/include
)
```

Указывает, где искать заголовочные файлы.

`PUBLIC` здесь значит, что папку `include` увидит сама библиотека `core`, а также
те target, которые будут подключать `core`.

</details>

<details>
<summary><b>target_link_libraries</b></summary>

<br>

```cmake
target_link_libraries(app
    PRIVATE core
)
```

Связывает один target с другим.

Здесь target `app` подключает target `core`, потому что в `main.cpp` используется
функция из библиотеки `core`.

`PRIVATE` значит, что зависимость нужна самому `app` и не должна передаваться дальше.

</details>

<details>
<summary><b>target_compile_features</b></summary>

<br>

```cmake
target_compile_features(core
    PUBLIC cxx_std_20
)
```

Указывает требования к возможностям компилятора для target.

В этом примере мы говорим, что для `core` нужен стандарт C++20.

</details>

<details>
<summary><b>find_package</b></summary>

<br>

```cmake
#find_package(Threads REQUIRED)
#find_package(Eigen3 3.3 REQUIRED NO_MODULE)
```

Ищет уже установленную библиотеку или пакет.

Сейчас эти строки закомментированы, потому что в проекте нет `Threads` и `Eigen`.
Они оставлены как пример на будущее.

</details>

</details>

## Пример Структуры проекта

```text
Template_CMake/
│
├── CMakeLists.txt
├── cmake/
│
├── include/
│   └── core/
│       └── math_utils.hpp
│
├── src/
│   ├── CMakeLists.txt
│   └── math_utils.cpp
│
├── app/
│   ├── CMakeLists.txt
│   └── main.cpp
│
├── tests/
│   ├── CMakeLists.txt
│   └── test_math.cpp
│
└── external/
```

**Основная идея:** в CMake можно создавать *target* практически для любой части проекта.

**Target** — это именованная сущность, которая по сути является контейнером для всех
свойств, связанных с модулем. Внутри такого контейнера могут храниться:

- исходные файлы,
- подключаемые библиотеки,
- директории заголовков,
- флаги компиляции,
- требования к стандарту языка,
- другие зависимости,
- и другие параметры сборки.

Иными словами, **target — это метка, описывающая модуль программы**. У этой метки
есть имя, и именно это имя обычно указывается первым аргументом в основных командах
CMake.

На практике таргеты чаще всего называют:

- по имени исполняемого файла — если таргет представляет приложение;
- по имени библиотеки — если таргет соответствует библиотеке или ее части.

После объявления одного или нескольких таргетов их можно настраивать, связывать друг
с другом зависимостями и выполнять другие операции, необходимые для организации
сборки проекта.

## Общие слова

Я ниже приведу план-структуру и пояснения что и зачем делается. Также смотрите в
самих `CMakeLists.txt` этого репозитория команды для этого примера.

У нас проект разделен так:

- `include` — хедеры, то есть объявления;
- `src` — реализация библиотеки;
- `app` — исполняемый файл;
- `tests` — отдельный исполняемый файл для простой проверки.

То есть мы не пишем весь код в одном `main.cpp`, а выносим полезную логику в
библиотеку `core`. Потом эту библиотеку можно подключить и к приложению, и к тестам.

## Главный CmakeLists.txt

Он создается в корне проекта. Я создаю в нем общие настройки проекта и подключаю
отдельные модули в нем: директории и библиотеки, которые будут нужны для сборки
всего проекта.

Основные команды в нем:

```cmake
cmake_minimum_required(VERSION 3.20)
```

Задает минимальную версию CMake. То есть если версия CMake ниже `3.20`, проект
лучше не собирать, потому что какие-то команды могут работать не так или вообще
отсутствовать.

```cmake
project(Template_CMake
    VERSION 1.0
    DESCRIPTION "Basic C++ project template with CMake"
    LANGUAGES CXX
)
```

Устанавливает имя метки целого проекта (**соответственно лучше называть проект по
названию вашего репозитория**). Оно нужно, если будете подключать свой проект в
другие, делиться им и по-хорошему для этого нужно будет прописать config, но об
этом потом. Сейчас имя проекта для простой локальной сборки особо не мешает и
просто описывает проект.

```cmake
set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)
```

Команды, задающие настройки проекта.

На пальцах:

- `CMAKE_CXX_STANDARD 20` — хотим C++20;
- `CMAKE_CXX_STANDARD_REQUIRED ON` — просим CMake не заменять стандарт на более старый;
- `CMAKE_CXX_EXTENSIONS OFF` — отключаем расширения компилятора, чтобы код был более переносимым.

```cmake
#find_package(Threads REQUIRED)
#find_package(Eigen3 3.3 REQUIRED NO_MODULE)
```

Еще в этом файле оставлены примеры команды *find_package*, но они закомментированы.
Сейчас в проекте нет `Threads` и `Eigen`, поэтому подключать их не нужно. Ниже я
еще напишу про эту команду.

```cmake
add_subdirectory(src)
add_subdirectory(app)

enable_testing()
add_subdirectory(tests)
```

`add_subdirectory` подключает модули. Напоминаю, что имена таргетов лучше называть
по смыслу ваших директорий или библиотек.

При выполнении главного файла CMake будет заходить в эти директории и читать
внутренние `CMakeLists.txt`. Там уже прописаны команды для конкретной части проекта.

`enable_testing()` включает поддержку тестов, чтобы потом можно было запускать их
через `ctest`.

Таким образом, главный CMake файл содержит общую информацию и легко редактируется.
Мы можем подключать просто директории, а всю реализацию оставлять во внутренних
CMake файлах, к которым сейчас и перейдем.

Смотрите подробнее в корневом файле.

## app

Так как мы хотим сделать исполняемый файл, то перейдем к файлу `CMakeLists.txt` в
директории `app`.

```cmake
add_executable(app main.cpp)
```

Эта команда делает таргет исполняемого файла *app*, который содержит файл
*main.cpp*, а также будет создаваться и сам исполняемый файл с именем *app*.

Следующая команда прилинкует к нашему таргету *app* таргет *core* с режимом
наследования, назовем это так, `PRIVATE`.

```cmake
target_link_libraries(app
    PRIVATE core
)
```

То есть все, чем будет наполнен таргет *core*, будет прилинковано в *app*. Таким
образом *main.cpp* будет слинкован с файлами, которые у нас располагаются в
библиотеке *core*, точнее в таргете *core*.

- `PRIVATE` означает: если мы *app* будем связывать дальше с другим таргетом,
  например `app0`, то он не получит то, что подключено к *app*. То есть
  **свойства таргета *core* не передадутся дальше по цепочке таргету *app0***.
- `PUBLIC`, соответственно, передал бы свойства дальше.

В директории `include/core` у нас лежит хедер `math_utils.hpp` и там нет CMake
файлов. Поэтому заглянем в `src`, где лежит `math_utils.cpp`.

## src

Первая команда:

```cmake
add_library(core)
```

Мы сделали таргет *core* типа библиотеки. Дальше наполним его, то есть подключим
к нему файл кода.

```cmake
target_sources(core
    PRIVATE
        math_utils.cpp
)
```

Следующим действием указываем, где лежат хедеры, которые нужны для сборки этой
библиотеки и для тех, кто будет эту библиотеку подключать.

```cmake
target_include_directories(core
    PUBLIC
        ${PROJECT_SOURCE_DIR}/include
)
```

Здесь `PUBLIC`, потому что хедер `core/math_utils.hpp` нужен не только самой
библиотеке *core*, но и приложению *app*, и тесту *test_math*.

Еще к библиотеке можно прилинковать необходимые таргеты:

```cmake
# target_link_libraries(core
#     PUBLIC
#         Eigen3::Eigen
#         Threads::Threads
# )
```

**Сейчас этого в проекте нет**, потому что в проекте нет `Eigen` и `Threads`.
Но если бы эти зависимости были найдены через `find_package`, то `Eigen3::Eigen`
и `Threads::Threads` тоже были бы таргетами.

`Eigen3` и `Threads` можно воспринимать как уже готовые внешние проекты или пакеты,
к которым мы обращаемся через CMake. Такое обращение к таргетам часто используется
после команды *find_package*. В таком случае CMake не обязан генерировать правила
сборки для этих библиотек с нуля, он просто находит уже подготовленные настройки.

```cmake
target_compile_features(core
    PUBLIC cxx_std_20
)
```

Здесь просто указали, какая версия языка будет использоваться при создании этого
таргета. То есть для *core* нужен C++20.

## tests

Это будет отдельный исполняемый файл с тестом для нашей функции.

```cmake
add_executable(test_math test_math.cpp)
```

Так как мы тестируем функцию *add* из файла *math_utils*, то подключаем таргет
*core*, в котором содержатся файлы, хедеры и настройки компиляции для библиотеки
*math_utils*.

```cmake
target_link_libraries(test_math
    PRIVATE core
)
```

Дальше регистрируем этот исполняемый файл как тест:

```cmake
add_test(NAME math_utils COMMAND test_math)
```

Сам тест здесь простой и ручной: без `assert`, без тестовых фреймворков. Он вызывает
функцию и возвращает `0`, если все хорошо. Если результат неправильный, возвращает
`1`.

## Как собрать проект

Сначала нужно дать CMake подготовить сборку:

```bash
cmake -S . -B build
```

`-S .` означает: исходники лежат в текущей директории.

`-B build` означает: все временные файлы сборки положить в директорию `build`.

После этого запускаем сборку:

```bash
cmake --build build
```

То есть CMake берет подготовленную папку `build` и уже через выбранную систему
сборки компилирует проект.

## Как запустить

Приложение:

```bash
./build/app/app
```

Тесты:

```bash
ctest --test-dir build
```

`ctest` зайдет в папку `build`, найдет зарегистрированный тест `math_utils` и
запустит исполняемый файл `test_math`.
