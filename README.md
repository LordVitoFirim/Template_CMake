# Базовая шпаргалка для CMake

Это учебный шаблон C++ проекта на CMake. Его цель — показать, как постепенно собрать
небольшой проект из библиотеки, приложения и тестов.

Проект не использует внешние зависимости. В `CMakeLists.txt` оставлены закомментированные
примеры `find_package`, чтобы позже было проще вспомнить, куда добавлять сторонние
библиотеки.

## 1. Зачем нужен CMake

Когда проект состоит из одного файла, его можно собрать напрямую компилятором:

```bash
c++ main.cpp -o app
```

Но как только появляются несколько `.cpp` файлов, папка `include/`, тесты,
отдельное приложение и внешние библиотеки, команда сборки быстро становится длинной.
Например, нужно вручную помнить:

- какие `.cpp` файлы компилировать;
- где лежат заголовочные файлы;
- какие библиотеки подключать;
- какой стандарт C++ использовать;
- какие флаги компилятора включить;
- как собрать приложение и тесты отдельно.

CMake решает эту задачу. Он не является компилятором. CMake — это система генерации
сборки. Мы описываем проект в `CMakeLists.txt`, а CMake на основе этого описания
создает файлы для конкретной системы сборки.

Например:

- на Linux это могут быть `Makefile` или `Ninja`;
- в CLion CMake используется внутри IDE;
- в Visual Studio CMake может создать проект под MSVC;
- на macOS можно собирать через AppleClang, Ninja или Make.

Главная идея: мы один раз описываем структуру проекта, а CMake помогает собирать
его на разных системах более одинаковым способом.

## 2. Как CMake смотрит на проект

В CMake лучше думать не отдельными командами компилятора, а целями.

Цель — это то, что нужно собрать:

- библиотека;
- исполняемый файл;
- тестовая программа.

В этом проекте есть три основные цели:

- `core` — библиотека с основной логикой;
- `app` — приложение, которое использует `core`;
- `test_math` — тестовая программа, которая тоже использует `core`.

Связь между ними выглядит так:

```text
math_utils.cpp + math_utils.hpp
        │
        ▼
   library: core
      │       │
      ▼       ▼
 executable  test executable
    app        test_math
```

Такой подход удобен: логика лежит в библиотеке `core`, а приложение и тесты просто
подключаются к ней. Если функция в библиотеке меняется, ее можно проверить тестами
без запуска основного приложения.

## 3. Два этапа работы CMake

У CMake обычно есть два разных этапа.

Первый этап — конфигурация:

```bash
cmake -S . -B build
```

На этом этапе CMake читает `CMakeLists.txt`, проверяет компилятор, настройки проекта,
пути к заголовкам, список целей и создает служебные файлы в папке `build`.

Второй этап — сборка:

```bash
cmake --build build
```

На этом этапе уже запускается настоящая сборка: компилируются `.cpp` файлы,
создаются библиотеки и исполняемые файлы.

Важно разделять эти этапы:

- `cmake -S . -B build` подготавливает сборку;
- `cmake --build build` выполняет сборку.

Папка `build/` не хранится в Git, потому что ее можно создать заново.

## 4. Почему структура проекта разделена на папки

Сначала была сделана такая структура:

```text
Template_CMake/
│
├── CMakeLists.txt
├── cmake/
│   └── CompilerWarnings.cmake
│
├── include/
│   └── core/
│       └── math_utils.hpp
│
├── src/
│   ├── CMakeLists.txt
│   └── math_utils.cpp
│
├── app/
│   ├── CMakeLists.txt
│   └── main.cpp
│
├── tests/
│   ├── CMakeLists.txt
│   └── test_math.cpp
│
├── external/
│
└── README.md
```

Что здесь за что отвечает:

- `CMakeLists.txt` в корне — главный файл сборки всего проекта.
- `include/` — публичные заголовочные файлы библиотеки.
- `src/` — реализация библиотеки.
- `app/` — исполняемая программа, которая использует библиотеку.
- `tests/` — тестовые программы.
- `cmake/` — дополнительные CMake-файлы, чтобы не перегружать корневой файл.
- `external/` — место под сторонние зависимости, если они появятся позже.

Такое разделение помогает не смешивать разные уровни проекта.

Заголовки лежат отдельно в `include/`, потому что это публичный интерфейс библиотеки.
Реализация лежит в `src/`, потому что она нужна для сборки библиотеки, но не обязана
быть видна пользователю библиотеки. Приложение лежит в `app/`, потому что это уже
конкретный способ запустить код. Тесты лежат в `tests/`, потому что они проверяют
библиотеку отдельно от приложения.

## 5. Корневой `CMakeLists.txt`

В корне проекта задается минимальная версия CMake:

```cmake
cmake_minimum_required(VERSION 3.20)
```

Потом описывается сам проект:

```cmake
project(Template_CMake
    VERSION 1.0
    DESCRIPTION "Basic C++ project template with CMake"
    LANGUAGES CXX
)
```

Здесь:

- `Template_CMake` — имя проекта.
- `VERSION 1.0` — версия проекта.
- `DESCRIPTION` — короткое описание.
- `LANGUAGES CXX` — проект использует C++.

Дальше задается стандарт C++:

```cmake
set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)
```

Это значит:

- используется C++20;
- CMake обязан включить именно этот стандарт;
- расширения компилятора вроде `gnu++20` отключены, нужен более переносимый режим.

Дополнительный файл с предупреждениями подключается так:

```cmake
include(cmake/CompilerWarnings.cmake)
```

Внешние зависимости пока не используются, но место для них оставлено:

```cmake
#find_package(Threads REQUIRED)
#find_package(Eigen3 3.3 REQUIRED NO_MODULE)
```

Подпроекты подключаются через `add_subdirectory`:

```cmake
add_subdirectory(src)
add_subdirectory(app)

enable_testing()
add_subdirectory(tests)
```

Порядок здесь важен: сначала собирается библиотека `core`, потом приложение и тесты,
которые эту библиотеку используют.

Корневой `CMakeLists.txt` отвечает за общие настройки всего проекта. Он не должен
знать слишком много деталей про каждый `.cpp` файл. Поэтому внутри папок `src/`,
`app/` и `tests/` лежат свои маленькие `CMakeLists.txt`.

Так проект читается сверху вниз:

```text
корень проекта
│
├── подключить общие настройки
├── собрать библиотеку
├── собрать приложение
└── собрать тесты
```

## 6. Библиотека `core`

В папке `src/` создается библиотека:

```cmake
add_library(core)
```

К ней добавляется файл реализации:

```cmake
target_sources(core
    PRIVATE
        math_utils.cpp
)
```

`PRIVATE` значит, что `math_utils.cpp` нужен только для сборки самой библиотеки.
Пользователям библиотеки этот `.cpp` файл напрямую не нужен.

Публичные заголовочные файлы подключаются так:

```cmake
target_include_directories(core
    PUBLIC
        ${PROJECT_SOURCE_DIR}/include
)
```

`PUBLIC` здесь важен: если приложение линкуется с `core`, оно автоматически узнает,
где искать заголовки из `include/`.

В CMake часто встречаются слова `PRIVATE`, `PUBLIC` и `INTERFACE`.

Их смысл такой:

- `PRIVATE` — настройка нужна только этой цели.
- `PUBLIC` — настройка нужна этой цели и тем, кто к ней подключается.
- `INTERFACE` — настройка нужна только тем, кто подключается к цели.

Пример из этого проекта:

```cmake
target_include_directories(core
    PUBLIC
        ${PROJECT_SOURCE_DIR}/include
)
```

Заголовки из `include/` нужны самой библиотеке `core`, но они также нужны приложению
`app` и тесту `test_math`, потому что оба подключают:

```cpp
#include "core/math_utils.hpp"
```

Поэтому здесь используется именно `PUBLIC`.

Стандарт C++ также закрепляется на уровне цели:

```cmake
target_compile_features(core
    PUBLIC cxx_std_20
)
```

И включаются предупреждения компилятора:

```cmake
enable_project_warnings(core)
```

## 7. Заголовочный файл

Публичный интерфейс библиотеки лежит в `include/core/math_utils.hpp`:

```cpp
#pragma once

namespace core
{
    int add(int a, int b);
}
```

Здесь объявляется функция `add`, но не описывается ее реализация.
Так другие части проекта знают, что такая функция существует.

Заголовочный файл можно воспринимать как обещание: функция есть, у нее такие параметры
и такой тип результата. А `.cpp` файл содержит само выполнение этого обещания.

## 8. Реализация библиотеки

Реализация находится в `src/math_utils.cpp`:

```cpp
#include "core/math_utils.hpp"

namespace core
{
    int add(int a, int b)
    {
        return a + b;
    }
}
```

Файл подключает заголовок и описывает, что именно делает функция.

## 9. Приложение

В папке `app/` создается исполняемый файл:

```cmake
add_executable(app main.cpp)
```

Потом приложение связывается с библиотекой:

```cmake
target_link_libraries(app
    PRIVATE core
)
```

`PRIVATE` значит, что библиотека `core` нужна только самому приложению.

После этой строки CMake понимает две вещи:

- перед сборкой `app` нужно собрать `core`;
- при компиляции `app` нужно использовать публичные настройки библиотеки `core`.

В `app/main.cpp` библиотека используется так:

```cpp
#include <iostream>

#include "core/math_utils.hpp"

int main()
{
    std::cout << "2 + 3 = "
              << core::add(2, 3)
              << '\n';

    return 0;
}
```

## 10. Тесты

Тест собирается как отдельная программа:

```cmake
add_executable(test_math test_math.cpp)
```

Он тоже подключается к библиотеке:

```cmake
target_link_libraries(test_math
    PRIVATE core
)
```

Чтобы CMake знал, что это именно тест, он регистрируется через CTest:

```cmake
add_test(NAME math_utils COMMAND test_math)
```

В самом тесте используются обычные `assert`:

```cpp
#include <cassert>

#include "core/math_utils.hpp"

int main()
{
    assert(core::add(2, 2) == 4);
    assert(core::add(-2, 2) == 0);
    assert(core::add(0, 0) == 0);
    assert(core::add(-2, -3) == -5);

    return 0;
}
```

Для маленького учебного проекта этого достаточно. Позже можно заменить `assert`
на полноценный тестовый фреймворк, например Catch2 или GoogleTest.

Тесты подключаются к той же библиотеке `core`, что и приложение. Это важная идея:
мы проверяем не копию кода, а настоящую библиотеку проекта.

## 11. Предупреждения компилятора

Файл `cmake/CompilerWarnings.cmake` нужен, чтобы включать предупреждения одинаково
для разных целей:

```cmake
function(enable_project_warnings target_name)
    if(MSVC)
        target_compile_options(${target_name} PRIVATE /W4)
    else()
        target_compile_options(${target_name} PRIVATE -Wall -Wextra -Wpedantic)
    endif()
endfunction()
```

Для Visual Studio используется `/W4`, а для GCC и Clang:

- `-Wall`
- `-Wextra`
- `-Wpedantic`

Это помогает раньше замечать подозрительный код.

Предупреждения подключены отдельной функцией, чтобы не копировать одни и те же флаги
в `src/CMakeLists.txt`, `app/CMakeLists.txt` и `tests/CMakeLists.txt`.

## 12. `.gitignore`

В проект добавлен `.gitignore`, чтобы не отправлять в Git временные файлы сборки:

```gitignore
build/
cmake-build-*/
CMakeCache.txt
CMakeFiles/
```

Смысл простой: исходный код хранится в Git, а результаты сборки можно получить заново.

## 13. Сборка проекта

Создать папку сборки и сконфигурировать проект:

```bash
cmake -S . -B build
```

Здесь:

- `-S .` — исходники лежат в текущей папке;
- `-B build` — файлы сборки нужно положить в папку `build`.

Собрать проект:

```bash
cmake --build build
```

После сборки внутри `build/` появятся результаты:

```text
build/
├── app/
│   └── app
├── src/
│   └── ...
└── tests/
    └── test_math
```

Точная структура внутри `build/` может немного отличаться в зависимости от генератора,
операционной системы и компилятора.

## 14. Запуск приложения

```bash
./build/app/app
```

Ожидаемый вывод:

```text
2 + 3 = 5
```

## 15. Запуск тестов

```bash
ctest --test-dir build
```

CTest найдет зарегистрированный тест `math_utils` и запустит исполняемый файл
`test_math`.

## 16. Общая логика проекта

Если коротко, весь проект работает так:

```text
1. Пишем публичный интерфейс в include/core/math_utils.hpp
2. Пишем реализацию в src/math_utils.cpp
3. Собираем это в библиотеку core
4. Подключаем core к приложению app
5. Подключаем core к тестам test_math
6. Регистрируем тесты в CTest
7. Собираем все через CMake
```

Главная польза такой структуры в том, что код не привязан только к одному `main.cpp`.
Библиотеку можно использовать из приложения, из тестов и из других будущих программ.

## 17. Что можно добавить дальше

Этот шаблон можно расширять постепенно:

- добавить внешнюю библиотеку через `find_package`;
- заменить `assert` на Catch2 или GoogleTest;
- добавить GitHub Actions для автоматической сборки;
- добавить установку проекта через `install`;
- добавить больше файлов в библиотеку `core`.
